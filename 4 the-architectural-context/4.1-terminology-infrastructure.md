# Terminology Infrastructure

## Terminology servers

The unifying piece of infrastructure — in deployments that have one — is the terminology server. It provides centralised, version-managed access to the code systems an organisation uses, with operations for concept lookup, code validation, value-set expansion, subsumption testing, and cross-map translation.

A single terminology server can host SNOMED CT (international edition plus national extension), ICD-10 and national variants, LOINC, RxNorm or ATC, ICPC-2, local codes, cross-maps between any pair of these, and reference value sets published by national programmes.

Every consumer system — the EHR, the FHIR server, the V2 integration engine, the analytics platform, the openEHR clinical data repository, decision-support services, AI tools — calls the same terminology server. This is what provides a single source of truth for coded clinical meaning across a mixed-architecture environment.

Most modern terminology servers expose FHIR terminology operations (`$lookup`, `$expand`, `$validate-code`, `$translate`, `$subsumes`), because FHIR has become the dominant terminology API standard. Well-known terminology servers used with SNOMED CT include Snowstorm (open source, from SNOMED International), Ontoserver (CSIRO, widely used in Australia and internationally), and the NHS England Terminology Server. Cloud-hosted and vendor-managed options are also available.

## Running SNOMED CT without a dedicated terminology server

A significant number of real-world SNOMED CT deployments operate without a separately managed terminology server. Four patterns are common.

---

**Pattern 1: SNOMED CT embedded inside the EHR**

The EHR vendor ships each product release with a SNOMED CT edition loaded internally. Concepts sit in the vendor's own database schema, search and pick lists are implemented in the vendor's UI, and lookup APIs are proprietary.

*Worked example.* A community-hospital EHR product used across approximately 200 hospitals in a region. The vendor issues new product builds every eight to twelve weeks. Each build includes an updated SNOMED CT international edition plus the vendor's own subset filters. When a clinician searches for a term, the search hits the EHR's internal terminology tables — there is no call to a separate terminology server. Outbound HL7 V2 messages carry SNOMED CT codes from those same internal tables.

*What works well.* Fast in-EHR search. Simple deployment architecture. The vendor manages SNOMED CT release currency. No separate infrastructure to operate.

*Where it breaks first.* The hospital's separate analytics warehouse cannot access the vendor's internal terminology tables. When the analytics team needs to expand a SNOMED CT value set or run a subsumption query, they must either maintain a separate copy of the SNOMED CT release in the warehouse (with the drift risk that creates) or add a terminology server alongside the EHR. The embedded-EHR pattern is well-suited to a single-system deployment but shows its limits as soon as a second consumer system needs SNOMED CT access.

---

**Pattern 2: Flat value sets baked into applications**

A subset of SNOMED CT is extracted at build time and shipped inside the application code as a static file — a JSON array, a database table, or a CSV. No runtime terminology lookup takes place.

*Worked example.* A bespoke referral form built for a regional cancer service. The form has a "primary tumour type" dropdown listing 42 SNOMED CT concepts. The 42 concepts were extracted from a terminology server once, in mid-2023, and shipped as a JSON file in the form's codebase. The form has been in production for three years. The JSON file is the value set — there is no runtime terminology dependency.

*What works well.* No runtime dependencies. No latency. Deployable in any environment.

*Where it breaks first.* Release currency. When a concept in the value set is inactivated in a subsequent SNOMED CT release, the form continues to offer it. When new, more appropriate concepts are added to SNOMED CT, the form does not benefit until a developer manually updates and redeploys the JSON file. The value set ages silently, and the gap between the form's value set and the current SNOMED CT edition widens with each release.

---

**Pattern 3: Static mapping tables in configuration files**

Legacy code-to-SNOMED CT translations are held as spreadsheets or configuration files, deployed alongside the integration engine or ETL job. The map is applied at message-transformation time; no live terminology API is involved.

*Worked example.* A hospital integration engine translating internal lab codes to SNOMED CT for outbound messaging. The mapping table is a CSV file of approximately 1,400 rows held in the integration engine's configuration folder. When the lab adds a new test, an integration engineer adds a row and redeploys the engine. The CSV is version-controlled. No terminology server is involved.

*What works well.* Fast. Simple. Transparent — any engineer can read the CSV and understand the mappings. Fits inside existing integration-engine change management.

*Where it breaks first.* Duplication and divergence across teams. When the analytics team needs the same lab-code-to-SNOMED CT translations for reporting, they either ask the integration team for the CSV and maintain their own copy, or independently reimplement the mappings. When the pharmacy team is also maintaining a drug-code-to-SNOMED-CT mapping table, there are now three separate CSV files with no mechanism to keep them aligned. Divergence is the default outcome.

---

**Pattern 4: Vendor-hosted terminology handling**

The EHR vendor operates terminology infrastructure in their own cloud, and the customer organisation never interacts with it directly. From the customer's perspective there is no terminology server to manage. From the vendor's perspective there is — it is the vendor's server, not the customer's.

*Worked example.* A large SaaS EHR product used by 40+ NHS trusts. The vendor operates a central terminology service that every trust's system calls for concept lookup and value-set expansion. From the trust's perspective, SNOMED CT just works — they do not run or manage terminology infrastructure. The vendor handles release management and value-set governance.

*What works well.* Customer complexity is minimised. SNOMED CT release currency is the vendor's responsibility. Customers with limited in-house terminology expertise get high-quality functionality without needing to build that expertise.

*Where it breaks first.* Governance flexibility. Local extensions, custom subsets, and bespoke cross-maps must be supported by the vendor — which may not align with the customer's timeline or requirements. Connecting a separate analytics platform or partner exchange to the same SNOMED CT layer requires either using the vendor's exposed APIs (if available) or duplicating the terminology work in a separately managed environment.

---

## Choosing the right approach

**One consumer system.** Any of the four no-server patterns can work indefinitely in a single-system deployment — one EHR, no separate analytics platform, no external partner exchange, no local extension content. Pattern 1 (embedded-in-EHR) is the most common answer.

**Two consumer systems.** As soon as a separate analytics platform, CDS engine, or HIE gateway enters the picture, the distributed patterns start to create coordination problems. Value-set drift between systems becomes a real risk within 12 months of the second system going live.

**Three or more consumer systems.** The pairwise coordination cost between each system's separate SNOMED CT holdings is significant. At three systems, a dedicated terminology server typically earns its operating cost quickly. At four or five, the case is clear.

**Local extension content.** Organisations maintaining a national extension, locally-authored subsets, or bespoke reference sets find embedded-EHR and static-mapping patterns operationally painful. A terminology server is the tool designed for exactly this job.

**External partner exchange with FHIR terminology API expectations.** Modern national programmes and cross-organisational data exchange increasingly assume access to the FHIR terminology operations (`$validate-code`, `$translate`, `$expand`). Without a server exposing those operations, participation requires additional bridging work in the integration engine.

The planning question is not "does this organisation need a terminology server?" — many organisations legitimately do not. It is "given how many consumer systems are planned, does the function the terminology server performs — a single source of truth for coded clinical meaning — need to be centralised, or can it reasonably remain distributed across individual systems?"
